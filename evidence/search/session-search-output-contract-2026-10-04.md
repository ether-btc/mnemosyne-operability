**Finding:** native `session_search` is not a safe canary interface for this boundary: its discovery projection includes snippets and its hydration returns the matched message. The underlying `SessionDB.search_messages` does accept `fields=["id", "session_id"]`; its finalizer then returns only those fields and omits context/snippet from the caller-visible rows. The SQL search still processes matching text locally. Its slow-search INFO logger includes the query, so the proposed one-off process must suppress the `hermes_state` logger before searching. `read_only=True` opens SQLite with `mode=ro`; if corrupt FTS triggers a write-attempt error path, the wrapper must stop with a generic failure and must never retry through a writable connection. This source trace supports the proposed interface; it does not prove that a live database, index, backup exclusion, egress boundary, or labeler setup is safe.
