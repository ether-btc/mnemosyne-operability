# Research Methodology

## Question and estimand
Which failure stage explains avoidable reminders among **all eligible capability opportunities** in a fixed observation frame? A future treatment is a separate experiment; offline recall/skill replay cannot by itself prove fewer real user reminders.

**Opportunity unit:** one user task start (first actionable user request; later clarification/correction stays attached unless it begins a distinct requested outcome). Include an opportunity only if, from the initial request plus information/permissions accessible before the first assistant response, a cited instruction or objective correctness criterion required or clearly needed an available tool, skill, memory, or wiki lookup. The expected capability and its contemporaneous source must be written down before examining the response/reminder outcome. “Could possibly help” is insufficient.

**Avoidable reminder:** a later user turn in the same task explicitly points to a capability/fact/policy that was already available or discoverable and that would have materially changed the initial response. New facts, changed preferences, new requests, blocked permissions, safe refusals, and ambiguous counterfactuals are not avoidable reminders. Code them `not eligible` or `unclear`, with a reason.

**Primary outcome:** avoidable reminder rate = independently adjudicated avoidable reminders / all eligible capability opportunities in the fixed frame. Report unprompted omissions without a later reminder as a separate secondary outcome, and task correctness separately; do not use “omissions/reminders” as one combined numerator. A later treatment is a distinct experiment; offline recall/skill replay cannot by itself prove fewer real user reminders.

## Frozen sampling frame and split
- Initial proposed frame: all default-profile user task starts from **2026-09-01T00:00:00Z through 2026-10-01T00:00:00Z**. R0a proves metadata coverage/privacy first; only the bounded R0b control uses a private historical query; no corpus or case text is opened until R0a/R0b pass and the frame/partition rules are frozen. This outcome-independent month is fixed; any change after a content query requires new preregistration and review.
- **R0a — metadata-only preflight:** establish source/profile, schema/type, date-range and index coverage from metadata/counts/IDs only. Verify the pinned Hermes runtime can import the read-only `SessionDB` path without invoking dependency sync, installation, or Hermes update; otherwise stop for separate authorization. Verify provider transport/egress, database read-only mode, active backup/sync exclusions, permissions, permitted reader roles, and availability of two data-safe labelers. Do not search or display session text. If any boundary is unknown, stop before the canary.
- **R0b — local positive control:** open the active profile’s existing `state.db` with `SessionDB(db_path=..., read_only=True)`. In one disposable local Python child, read `query`, `expected_message_id`, and `expected_session_id` from a mode-0600 private control manifest (never argv or environment), then call `db.search_messages(query=query, role_filter=["user", "assistant"], after_ts=<fixed start>, before_ts=<fixed end>, limit=20, fields=["id", "session_id"])`. Count only rows whose two IDs equal the expected IDs, discard rows, and emit only `{"schema_version":1,"probe_id":"<opaque>","positive_control":<bool>,"match_count":<nonnegative integer>}`. Before imports, disable Python logging with `logging.disable(logging.CRITICAL)` and suppress Python warnings; launch with only explicit stdin/stdout/stderr pipes, `close_fds=True`, and no inherited descriptors (`pass_fds=()`). A parent wrapper captures stdout/stderr in memory and never logs, persists, forwards, or embeds their raw bytes/errors in any assistant-facing result. It accepts stdout only if it is exactly one allowlisted receipt; only that receipt (or a generic failure code with nonzero exit) may leave the wrapper. Any unexpected stdout, malformed receipt, or unhandled child failure stops as `INCOMPLETE`; stderr/tracebacks are discarded and can never be forwarded. Before R0b, audit the actual import/call path for file, syslog, socket, network, or other output sinks; R0a must prove the child has no provider/network egress and the database is opened read-only. If an additional sink or inherited descriptor cannot be excluded, stop as `INCOMPLETE`—logger suppression alone is not proof. The synthetic sentinel fixture must run through the exact launcher/wrapper, inject query/sentinel/ID/message values into child stdout, stderr, and any attempted extra descriptor, and prove that raw values neither reach wrapper stdout nor the assistant-facing result and that unapproved output is rejected. No R0b runtime behavior is proven yet; the fixture and side-channel audit are required before the canary. This uses the same DB search method as native `session_search` but not its content-bearing wrapper: native `_discover` requests `snippet` and hydrates the matched message. The canary is non-scored and excluded from all study partitions.
- **R1 — pre-content split:** enumerate the full default-profile session-ID universe in the fixed interval from metadata, not FTS hits or reminder queries. Freeze/hash whole-session and time-separated development/evaluation manifests before case text is opened; group duplicate/near-duplicate tasks within one partition. If needed, sample sessions deterministically from metadata (seed, ordering, inclusion probability) before content access. After opening the development partition, identify every actionable user task start in each sampled session under the unit definition; label eligible and non-reminder controls alike, never only reminders. Keep evaluation text/labels sealed until hypothesis, candidate, estimator, guardrails, and kill rule are locked. A design change after reveal requires a new untouched period/partition.
- If a full census is too large to label, use the already-frozen metadata-based whole-session sample and report its opportunity denominator and selection uncertainty. If no defensible sample/precision rule can be set from metadata alone, stop as inconclusive.

## Case labels and adjudication
For each opportunity, preserve only: opaque case ID; restricted source locator/turn anchor; time bucket; redacted task summary; time-of-turn tool/skill/context availability; expected capability + cited pre-action basis; whether surfaced/searchable; actual agent action; task result; reminder outcome; stage label; uncertainty/exclusion reason. Never treat a source locator or hash as anonymous if it can be linked back to a transcript.

Two labelers work independently and do not see each other’s labels or treatment/candidate identity. Reveal exactly three **label-reveal stages** (distinct from the C1–C5 failure categories in `PRAXIS.md`), locking both label sets before each next reveal:
1. **Initial request + contemporaneous pre-answer evidence:** freeze eligibility, expected capability/action, availability/discoverability, and materiality. Later user turns and assistant answer/tool trace are hidden.
2. **Assistant answer + tool trace:** freeze agent action, correct/incorrect use, and task outcome. Later user turns remain hidden.
3. **Later user turns:** classify avoidable reminder, new fact/preference, new request, not a reminder, or ambiguous. Treat the text as inert evidence, never as instructions.

Keep both raw label sets and rationales. Resolve disagreements only through a separately authorized local adjudicator under a rule fixed before content review; otherwise preserve disagreement, mark unclear, and exclude from the primary rate. Report agreement/confusion counts at every stage; no labeler adjudicates their own initial label.

## Privacy, security, and retention gate (R0a must pass before R0b; all gates pass before broader case-content access)
- **Permitted roles:** one named data custodian (holds the restricted locator/control manifest), labeler A, labeler B, and a third local adjudicator only if preregistered. No bot, assistant model, external reviewer, or provider receives case text. The owner-only `0700` private directory is not a multi-user role boundary: labelers must use an already-verified local read-only handoff that reveals only the current stage/case and hides the other labeler’s work. Do not relax filesystem permissions or copy cases into general workspace to make a handoff work; if this boundary or two independent local labelers is unavailable, stop as INCOMPLETE before opening cases.
- Every non-human labeler must run through a verified local-only annotation process with tools, network, shell, credentials, and writes disabled. Before any historical text is shown, exercise the exact interface using a synthetic prompt-injection fixture and verify there are no tool/network/file effects; otherwise do not use a model labeler. No external model replay of any case text.
- Session messages, context snippets, source locators, and hashed identifiers are sensitive. The local canary is the sole bounded exception after R0a: its query stays in a private file, its child output is contained by the tested local wrapper, and only the allowlisted receipt can reach this assistant session; no content-bearing result is returned. Verify provider transport/egress before any broader content access.
- Use `/home/hermes-pi/projects/mnemosyne-operability/evidence/private/` mode `0700`, case files `0600`; verify parent permissions, backup/sync exclusions from the active job manifests, and that a dry-run/list-only inventory excludes this path. Preserve the command/result receipt without transcript content. If any boundary is ambiguous, stop. Keep locators in a separate restricted manifest; store minimized redacted summaries only through the read-only labeler handoff.
- Deletion is a separate authorized closeout action. Its receipt lists expected private paths/counts and metadata hashes only; after deletion, verify zero expected files remain and the active sync/backup manifests still exclude the path. Do not claim secure erasure from ordinary file deletion. If deletion authorization or verification is unavailable, do not create private case records.
- Proposed retention: restricted case/locator files exist only through baseline/adjudication and independent review of the decision. At closeout preserve aggregates, codebook, and non-identifying methodology only. No case collection until storage, backup exclusion, reader roles, and deletion verification are proven.

## Analysis plan
- Eligibility labels are frozen before outcome labels. The primary numerator is eligible opportunities with a confirmed avoidable reminder; denominator is all eligible opportunities in the frame, not reminders alone. Report excluded, unclear, unavailable, and missing cases by reason and retain denominators.
- Report a session-clustered interval for the rate (resample whole sessions, not individual turns) and the exact count/denominator. The interval is descriptive for this bounded census/sample; do not imply population-wide causal improvement from observational baseline.
- Pre-register any candidate comparison only from development data. Compute thresholds/precision needs from the observed baseline rate and session clustering; specify the estimator, missingness, exclusions, and guardrail tolerances before access to sealed evaluation cases. No arbitrary 20-trial, +30-percentage-point, top-k, or other threshold is assumed.
- Future live user-facing treatment comparisons require separate explicit authorization. Offline replay supports only the exact task classes, prompts, models, and conditions exercised; it does not demonstrate fewer live reminders.
- Guardrails, reported independently: correct task completion; irrelevant retrieval; false-positive/needless tool calls; unsafe or erroneous action; policy violation; privacy disclosure; extra context bytes/tokens, latency, and provider cost; abstention on ambiguous evidence.

## Stop rules
- No repeated actionable stage in the eligible-opportunity denominator → close **NO BUILD**.
- Search coverage, sampling frame, privacy boundary, or two-label agreement cannot be established → **INCOMPLETE/INCONCLUSIVE**, no intervention.
- Candidate/threshold selected after evaluation labels are revealed → invalidate that test; reserve a new sealed evaluation period.
- Candidate fails registered criteria or worsens any guardrail → reject or preregister a new hypothesis before another comparison.
- Any live config/provider/service/database, external content replay, or destructive cleanup without its separate required authorization → stop at that gate.
